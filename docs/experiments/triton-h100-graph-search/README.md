# Triton H100 search under the CUDA Graph reward

This experiment moves from the local-overlay Graph validation to a published,
digest-pinned worker image. The image is built from committed source
`0f8debe199374e6149a96d778e42a8504f9dee79` using
[`Dockerfile.triton-h100-graph`](../../../Dockerfile.triton-h100-graph) on the
previously validated Triton 3.9 worker base. The Docker Hub registry digest
(checked with `skopeo inspect docker://` after push) is
`docker.io/saarora/gpu-kernel-mcts@sha256:1e02c618f5a99b7f212522e0623131c3c26fb27c76834401b4a6bed54fad7874`.
No local package overlay is used. Search records must use
`triton_h100_cuda_graph_v1` for the root, candidates, cuBLAS, and CUTLASS.
The [trace auditor](audit.py) checks these records after each completed run.

## Sequence

1. Run a deterministic `B_gen=1` Triton MCTS smoke through the published
   worker, then inspect the SQLite timing contract and worker cleanup.
2. Pair pure-Triton freeform MCTS and pure-Triton freeform sequential search
   on the same worker for each seed. Use GLM-5.3, the same packaged root,
   `B_gen=25`, one repair allowance, hidden parent NCU, no compiler/dataflow/
   H100 graph prompt view, and `lightweight_v1` lazy NCU collection. The
   [paired runner](../triton-h100-freeform-compare/run_paired.py) supports
   `--no-overlay`, `--image`, and `--output-dir` for this cohort.
3. Compare best verified Graph latency by generation call, validity,
   strategies/actions, and prompts. Keep historical per-call CUDA-event
   results in a separate cohort.

## Results

The first smoke attempt used Podman's local `RepoDigests` value, which did not
resolve on Docker Hub. Nebius rejected the image before worker startup, and
the provider deleted its VM and boot disk. The trace is archived as
`output/smoke-local-digest-failed.sqlite`; it has no candidate evaluations.
The retry used the registry digest above. Its deterministic `B_gen=1` MCTS
smoke completed with one valid candidate, two nodes, and two lazy NCU profiles.
The [SQLite trace](output/smoke-b1.sqlite) passed `audit.py`: root, cuBLAS,
CUTLASS, candidate benchmark, and both nodes recorded
`triton_h100_cuda_graph_v1`. Graph medians were 816.400 µs for the root,
546.144 µs for the smoke candidate, 173.584 µs for cuBLAS, and 309.504 µs
for CUTLASS. The smoke candidate is only a wiring check, not an optimized
kernel. Nebius showed no remaining VM or boot disk after completion.

## Paired freeform search

Two same-worker seed pairs completed at configured and consumed `B_gen=25`
per arm. Seed 1 ran sequential then MCTS; seed 2 ran MCTS then sequential.
Each pair has one environment manifest ID and identical root/vendor
calibrations within that worker. All four SQLite traces passed `audit.py`:
every root, vendor, node, and benchmarked-generation record used
`triton_h100_cuda_graph_v1`. The SQLite traces are local and Git-ignored;
the runner exported each best source and a small JSON result beside it.

| Seed | Arm | Best Graph median, µs | Found at `B_gen` | Valid / 25 | Same-worker cuBLAS, µs |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 | [Sequential](output/seq-glm53-s1-b25-graphv1-best.py) | 180.384 | 22 | 20 | 173.856 |
| 1 | [MCTS](output/mcts-glm53-s1-b25-graphv1-best.py) | **177.600** | 15 | 21 | 173.856 |
| 2 | [MCTS](output/mcts-glm53-s2-b25-graphv1-best.py) | 181.968 | 6 | 17 | 171.920 |
| 2 | [Sequential](output/seq-glm53-s2-b25-graphv1-best.py) | **178.064** | 7 | 20 | 171.920 |

MCTS won seed 1 by 2.784 µs, while sequential won seed 2 by 3.904 µs.
The best observed kernel, seed 1 MCTS, was 3.744 µs (2.15%) above its
same-worker cuBLAS calibration. These are one benchmark per search candidate
and only two paired seeds. The winners' 30-sample standard deviations were
about 1.2–1.4 µs, and run-to-run GPU drift may be larger; repeat the winners
on one worker before treating a few microseconds as a stable ranking.

The seed 1 MCTS winner was generated by a freeform source rewrite at call 15:
it changed a grouped pointer-load GEMM into a persistent, SM-strided Triton
kernel using tensor descriptors for A, B, and C. Its recorded compiler
resources were 156 registers per thread, 213,016 bytes of static shared
memory, and zero spills. The seed 1 sequential winner used a persistent
pointer-load loop. The seed 2 MCTS winner used a grouped pointer-load tile;
the sequential winner used a persistent pointer-load loop. These source
differences identify plausible mechanisms, but the traces alone do not
isolate the cause of their small latency differences.

The two policies still use different prompt/response protocols. MCTS asks
for raw source; sequential asks for a JSON choice, hypothesis, and source
and later receives recent acceptance/failure feedback. Both hide NCU,
compiler, dataflow, and H100 graph views from the model, while collecting
`lightweight_v1` profiles for trace analysis. The model's sampling is not
guaranteed to be controlled by the search seed. This pair validates search
under the new reward and shows both policies can reach near-cuBLAS kernels;
it does not establish a winning search policy.
